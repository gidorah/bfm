01 /

The job in three verbs.

BFM runs beside a PostgreSQL replication cluster. It combines database observations with node-level operations, and offers a web interface and a Bash CLI for operators.

◎

Observe

Query PostgreSQL roles, replication state, WAL positions, and timelines. Track cluster health and the availability of a paired BFM instance.

⑂

Decide

Classify cluster health, retry a missing primary, inspect replication progress, and choose an eligible replacement using configured priorities.

↗

Act

Ask MiniPG to promote, move a virtual IP, and rewind or rebuild other nodes. Operators can also request switchover and reinitialization.

Two kinds of “primary.” An active BFM manages the cluster; a PostgreSQL primary accepts database writes. In the code these are called isMasterBfm and masterServer. Keep them separate as you read.

STEP 01 / OWNERSHIP

First, decide who is watching.

checkCluster() uses the last peer status. No peer, a passive peer, or an unreachable peer makes this BFM active. When the peer is active, this instance copies its saved status to the local snapshot and returns.

checkCluster()
  paused? → skip
  peer active? → copy peer snapshot; return
  otherwise → become active BFM
ClusterCheckScheduler.java → checkCluster()
Read the branches, not just the happy path. This is an orientation to the current implementation. An all-inaccessible cluster becomes IGNORING; multiple-primary cases have their own recovery branches. WAL/timeline leader selection and priority-based promotion selection are separate methods.

05 /

From checkout to first contribution.

Use system Maven 3.9.x with Java 21, from the repository root. The committed Maven wrapper is missing its support directory.

01 — Build the application
mvn -pl app -am package -DskipTests
02 — Run the existing test
mvn -pl app test -Dtest=BfmApplicationTests

The current suite is a placeholder plain-JUnit test, without a Spring context. A passing run does not exercise failover or a real PostgreSQL cluster.

03 — Run with your local configuration
mvn -pl app spring-boot:run \
  -Dspring-boot.run.arguments=--spring.config.location=file:./application.properties

Prepare your own configuration first; with this app-module run, place it in app/application.properties. Start from the packaged template, replace its cluster addresses and credentials with your development cluster’s values, and configure the matching MiniPG agents. The application has no bundled application.properties.

Configuration worth knowing

server.pglist
Comma-separated host:port entries, optionally suffixed with |priority. Higher priority wins the normal promotion selection; 0 excludes a node from that path.
watcher.cluster-port / watcher.cluster-pair
The BFM listener and optional peer address. Set ports explicitly: the Java listener default is 9995, while the CLI defaults to 9994.
bfm.watch-strategy
availability is the automatic mode; manual requests operator intervention. The strategy endpoint accepts only A or M, despite extra modes named in the template comments.
bfm.data-loss-tolerance
Used in the no-primary path with WAL position information. Also follow bfm.status-file-expire for snapshot-age handling.
bfm.basebackup-slave-join
Controls the base-backup fallback after rewind fails. bfm.ex-master-behavior controls stop/rejoin behavior in a multiple-primary branch.
bfm.user-crypted
Enables AES-GCM decryption of configured secrets. Generate encrypted values through BFM’s POST /bfm/encrypt/{clearStr} endpoint.
Working-directory state. The status snapshot and logs are relative to the running process. The repository’s bfm_status.json is a sample. The literal profile value in BfmApplication is not a configured profile-selection workflow.

Translate the vocabulary

Primary / replica
The source uses MASTER / SLAVE. A primary without connected replicas is MASTER_WITH_NO_SLAVE.
Active / passive BFM
The manager’s role, determined using peer activity. The passive branch copies the active peer’s saved status.
WAL / LSN
PostgreSQL’s write-ahead log and a position in that log. BFM observes these to reason about replication progress and possible loss.
Timeline
A PostgreSQL recovery-history identifier. Leader helpers compare timeline IDs and WAL positions.
MiniPG
The external node agent that BFM asks to manage PostgreSQL processes, promotion, recovery, and virtual IPs.
VIP
A virtual IP moved to the promoted node, giving clients a stable connection address.
Failover / switchover
Failure-driven promotion versus an operator-requested primary change. Switchover and reinit require the active BFM and pause checks internally.
Rewind / rebase
Rewind reconciles a node with the selected primary; the rebase helper requests a base-backup rebuild as a configured fallback.
